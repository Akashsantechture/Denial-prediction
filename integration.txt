────────────────────────────────────────────────────────────────────────────────
1. SYSTEM OVERVIEW
────────────────────────────────────────────────────────────────────────────────

ClaimAI consists of three runtime components:

  ┌─────────────────────────────────────────────────────────────────────────┐
  │  BROWSER (SPA)           http://127.0.0.1:8000                          │
  │  frontend/index.html                                                     │
  │  Vanilla JS + Plotly.js                                                  │
  │  Served as static files by the Prediction API                           │
  └──────────────┬──────────────────────────────┬───────────────────────────┘
                 │ POST /predict_user_claim      │ POST /analyst/session
                 │ GET  /health                  │ POST /analyst/chat
                 ▼                               │ DELETE /analyst/session/:id
  ┌──────────────────────────────┐               ▼
  │  PREDICTION API              │  ┌────────────────────────────────────┐
  │  model2main.py            │  │  AI ANALYST MICROSERVICE           │
  │  FastAPI + XGBoost v1.5      │  │  ai_analyst/main.py                │
  │  Port 8000                   │  │  FastAPI + Gemini (Vertex AI)      │
  │                              │  │  Port 8060                         │
  │  Also serves frontend/       │  │                                    │
  │  as StaticFiles mount        │  │  Depends on:                       │
  └──────────────────────────────┘  │   - PostgreSQL (sessions + msgs)   │
                                     │   - Google Cloud Vertex AI         │
                                     └────────────────────────────────────┘

Both backend services are independent processes (or Docker containers).
The frontend talks to both directly from the browser via fetch().
Neither service calls the other — the browser is the orchestrator.


────────────────────────────────────────────────────────────────────────────────
2. SERVICE RESPONSIBILITIES
────────────────────────────────────────────────────────────────────────────────

  SERVICE                 RESPONSIBILITY
  ──────────────────────────────────────────────────────────────────────────
  Prediction API          Accepts a raw claim JSON, runs the XGBoost v1.5
  (port 8000)             inference pipeline (model2main.py), returns denial
                          probability, risk level, SHAP feature contributions
                          computed by TreeExplainer, and SHAP feature
                          interactions.
                          Also serves the frontend SPA as static files.

  AI Analyst              Accepts the full claim intelligence (claim facts
  Microservice            + prediction result + SHAP values) and creates a
  (port 8060)             persistent conversational session backed by
                          PostgreSQL.  On each chat turn it sends the claim
                          intelligence, conversation history, and the user
                          message to Gemini (Vertex AI) and returns a
                          grounded natural-language explanation.

  Frontend SPA            Collects the claim form, calls both backends,
  (browser)               renders Plotly charts, and drives the AI chat
                          drawer.  Falls back to a local rule-based engine
                          if the AI Analyst is unreachable.
  ──────────────────────────────────────────────────────────────────────────

3. FULL REQUEST FLOW (STEP BY STEP)
────────────────────────────────────────────────────────────────────────────────

STEP 1 — User submits claim form
  app.js  handleSubmit()
    → collectPayload() (or JSON textarea)
    → showSpinner(true)
    → Chat.clear()                 ← deletes previous analyst session

STEP 2 — Prediction API call
  api.js  API.predict(payload)
    → POST http://127.0.0.1:8000/predict_user_claim
       Body: { diagnosis_code, activity_code, claim_net, ... }

  model2main.py pipeline:
    1. Pydantic validation (UserClaimInput)
    2. add_categorical_features()   → icd_category, cpt_category
    3. engineer_features()          → *_log transforms, high_cost_flag
    4. build_model_dataframe()      → exact 19-feature DataFrame
    5. XGBoost predict_proba()      → denial probability
    6. SHAP TreeExplainer           → per-feature contributions
    7. Risk classification          → HIGH / MEDIUM / LOW
    8. PredictionResponse           → returned to browser

  Browser receives:
    {
      denial_probability_pct,  is_high_risk,  risk_level,
      action_recommendation,
      explanation: {
        base_value, final_model_value,
        top_drivers:        [{ feature, shap_value, direction, ... }],
        supporting_factors: [...],
        all_features:       [...],
        interactions:       [{ feature_1, feature_2, interaction_value, ... }]
      }
    }

STEP 3 — Charts and tabs rendered
  app.js dispatches result to:
    Charts.gauge()              → denial probability gauge
    Charts.denialReasonBar()    → SHAP factor distribution (Overview tab)
    Charts.waterfall()          → SHAP waterfall (SHAP tab)
    Charts.featureScatter()     → feature value vs SHAP scatter
    Charts.dependence()         → claim amount dependence chart
    ICD.renderTable/Heatmap()   → ICD Drill-Down tab
    Interactions.renderPairs/
      SHAPHeatmap/DenialHeatmap → Interactions tab

STEP 4 — AI Analyst session created (non-blocking, runs after greeting)
  chat.js  Chat.init(payload, result, contributions)
    1. Greeting bubble rendered immediately from local SHAP data (no network wait)
    2. _initLLMSession() fires asynchronously:
         → _buildClaimIntelligence(payload, result, contributions)
           Constructs:
             {
               claim:   { all raw claim fields },
               prediction: { probability, risk_level, action },
               shap_explanation: result.explanation,   ← full API SHAP object
               top_shap_contributions: [               ← top 10 from shap.js
                 { feature, shap_value, direction }, ...
               ]
             }
         → AnalystAPI.createSession(claimIntelligence)
           POST http://127.0.0.1:8060/analyst/session
           Body: { claim_intelligence: { ... } }

  AI Analyst receives session request:
    analyst_service.py  create_session()
      → session_manager.create_session()
          Writes two PostgreSQL rows atomically:
            analyst_sessions          (session_id, status, timestamps)
            analyst_claim_intelligence (session_id, evidence JSON)
      → Returns session_id (UUID)

  Browser receives { session_id }
    _sessionId stored in chat.js
    _mode set to 'LLM'
    Mode badge updated to "✦ Gemini AI"

  If the microservice is unreachable or returns an error:
    _mode stays 'RULE_BASED'
    Mode badge shows "⚡ Rule-based"
    All subsequent chat turns use the local rule engine — no further
    network calls to port 8060

STEP 5 — User sends a chat message
  chat.js  Chat.send(userMessage)
    1. User bubble appended
    2. "Thinking…" placeholder bubble appended
    3. _generateResponse(userMessage) called:

       IF _mode === 'LLM':
         AnalystAPI.chat(_sessionId, userMessage)
           POST http://127.0.0.1:8060/analyst/chat
           Body: { session_id, message }

         AI Analyst receives chat request:
           analyst_service.py  chat()
             1. session_manager.get_claim_intelligence(session_id)
                  Reads evidence JSON from PostgreSQL
             2. session_manager.add_message(session_id, role='user', content)
                  Writes user message to analyst_messages table
             3. session_manager.get_messages(session_id)
                  Retrieves full conversation history (ordered by created_at)
             4. llm_reasoner.generate_response(
                    claim_intelligence,
                    conversation,
                    user_message
                )
                  Builds structured prompt containing:
                    - SYSTEM_PROMPT (strict evidence-grounding rules)
                    - CLAIM INTELLIGENCE JSON block
                    - CONVERSATION HISTORY JSON block
                    - CURRENT USER QUESTION
                  Calls Gemini via Vertex AI:
                    client.models.generate_content(
                        model='gemini-2.5-flash',
                        temperature=0.1
                    )
             5. session_manager.add_message(session_id, role='assistant', content)
                  Writes Gemini answer to analyst_messages table
             6. Returns answer string

         Browser receives { session_id, answer }
         Thinking placeholder replaced with Gemini answer

       IF _mode === 'RULE_BASED' (or LLM call failed):
         _generateRuleBased(userMessage) runs locally
         Keyword regex matching produces a deterministic answer
         Thinking placeholder replaced with rule-based answer
         If failure was unexpected (was in LLM mode):
           "⚡ Local response — AI Analyst temporarily unavailable." notice appended

STEP 6 — Session cleanup
  When user submits a new claim or page is unloaded:
    Chat.clear()
      → AnalystAPI.deleteSession(_sessionId)   (fire-and-forget)
        DELETE http://127.0.0.1:8060/analyst/session/{session_id}

      AI Analyst CASCADE-deletes:
        analyst_sessions row
        → analyst_messages rows       (CASCADE)
        → analyst_claim_intelligence  (CASCADE)

5. FALLBACK BEHAVIOUR
────────────────────────────────────────────────────────────────────────────────

The rule-based engine in chat.js is a complete fallback — it does not
degrade gracefully, it is fully feature-complete for standard questions.

  SCENARIO                              BEHAVIOUR
  ──────────────────────────────────────────────────────────────────────────
  Port 8060 unreachable on startup      _mode = RULE_BASED from the start.
                                        Badge shows "⚡ Rule-based".
                                        User sees no error — answers are
                                        instant from the local engine.

  Session creation returns HTTP error   Same as above — falls back cleanly.

  Individual chat call fails            That single message falls back to
                                        rule-based.  _mode stays LLM so
                                        the next message tries Gemini again.
                                        A subtle notice is appended:
                                        "⚡ Local response — AI Analyst
                                        temporarily unavailable."

  Gemini quota / 500 from Vertex AI     analyst_service raises RuntimeError.
                                        FastAPI returns HTTP 500.
                                        AnalystAPI.chat() returns
                                        { ok:false, detail }.
                                        chat.js falls back for that turn.

  Gemini timeout (>30 s)                AbortController fires.
                                        AnalystAPI.chat() returns
                                        { ok:false, detail:'timed out' }.
                                        Rule-based answer used for that turn.
  ──────────────────────────────────────────────────────────────────────────

7. POSTGRESQL SCHEMA
────────────────────────────────────────────────────────────────────────────────

Tables created by ai_analyst/db/models.py on first startup (init_db()):

  analyst_sessions
  ─────────────────
  session_id     VARCHAR(36)   PK
  model_version  VARCHAR(100)  nullable
  llm_model      VARCHAR(150)  nullable
  status         VARCHAR(30)   'active' | 'completed' | 'deleted' | 'error'
  created_at     TIMESTAMPTZ
  updated_at     TIMESTAMPTZ

  analyst_claim_intelligence
  ───────────────────────────
  session_id  VARCHAR(36)   PK, FK → analyst_sessions(CASCADE)
  evidence    JSON          full claim intelligence blob
  created_at  TIMESTAMPTZ
  updated_at  TIMESTAMPTZ

  analyst_messages
  ──────────────────
  id          VARCHAR(36)   PK (UUID)
  session_id  VARCHAR(36)   FK → analyst_sessions(CASCADE), indexed
  role        VARCHAR(30)   'user' | 'assistant' | 'system'
  content     TEXT
  created_at  TIMESTAMPTZ

  analyst_request_logs
  ──────────────────────
  request_id      VARCHAR(36)   PK (UUID)
  session_id      VARCHAR(36)   nullable, indexed
  endpoint        VARCHAR(150)
  status          VARCHAR(30)   'success' | 'error' | 'timeout'
  latency_ms      INTEGER       nullable
  llm_model       VARCHAR(150)  nullable
  error_message   TEXT          nullable
  metadata_json   JSON          nullable (non-PHI metadata only)
  created_at      TIMESTAMPTZ

Cascade policy: deleting an analyst_sessions row automatically removes all
associated analyst_messages and analyst_claim_intelligence rows.

9. RUNNING LOCALLY (WITHOUT DOCKER)
────────────────────────────────────────────────────────────────────────────────

Prerequisites:
  - Python 3.11+
  - PostgreSQL running locally (default: localhost:5432)
  - Google Cloud credentials configured (gcloud auth application-default login
    OR credentials.json in project root)

Terminal 1 — Prediction API:
  uvicorn model2main:app --reload --port 8000

Terminal 2 — AI Analyst Microservice:
  uvicorn ai_analyst.main:app --reload --port 8060

Browser:
  http://127.0.0.1:8000

10. RUNNING WITH DOCKER
────────────────────────────────────────────────────────────────────────────────

10.1  Build images (run from project root)
───────────────────────────────────────────
  # Prediction API
  docker build -t denial-prediction-api .

  # AI Analyst Microservice
  docker build -t denial-analyst -f ai_analyst/Dockerfile .

10.2  Run containers
─────────────────────
  # Prediction API (serves frontend + XGBoost inference)
  docker run -d \
    --name prediction-api \
    -p 8000:8000 \
    denial-prediction-api

  # AI Analyst Microservice
  docker run -d \
    --name analyst \
    -p 8060:8060 \
    --env DATABASE_URL="postgresql+psycopg2://postgres:2004@host.docker.internal:5432/Denial-prediction" \
    --env GOOGLE_CLOUD_PROJECT="your-gcp-project-id" \
    --env GOOGLE_APPLICATION_CREDENTIALS="/app/credentials.json" \
    denial-analyst

  Note: host.docker.internal resolves to the host machine on Docker Desktop
  (Windows/macOS).  On Linux use --network host or a Docker network.

10.3  docker-compose (recommended for local development)
──────────────────────────────────────────────────────────
  Create docker-compose.yml in the project root:
